# NexusPiercer — Makeover Roadmap

_Generated 2026-08-09 from the 13-agent audit. See [FINDINGS.md](FINDINGS.md) for the 200-item register._

## Verdict

NexusPiercer is a competently-written codebase wrapped in a governance and verification shell that is almost entirely fictional, and that gap is the actual product defect. Nothing has ever run in CI (the workflow sits at the repo root where Actions cannot see it), three static-analysis plugins have never been downloaded let alone executed, the coverage gate is set 40 points below actual coverage so it can only ever report success, and the release workflow produces unsigned artifacts against a decommissioned Sonatype endpoint — so the published 1.0.8 on Maven Central is untraceable to any commit (zero tags) and unverified by any machine. The architecture has a fundamental problem that must be named plainly: this is not one library, it is three disjoint codebases sharing a package name — a Java stack that owns the entire Spark surface but cannot reconstruct data, a Groovy stack that owns the only working round-trip but has no Spark integration and isn't even Serializable, and a 6,130-LOC Iceberg converter island reachable from nothing but its own tests; the two flatten stacks emit mutually incompatible key encodings, so the library's headline promise (flatten, then reconstruct) is not satisfiable through any single supported path. Underneath that sits the worst defect in the repo: the flattened field name is an unescaped String, so `{user_id:1}` and `{user:{id:1}}` produce the identical key — meaning reconstruction is provably lossy for the snake_case schemas that dominate this library's entire target domain, and the "perfect reconstruction" claims in the Javadoc are false. The Groovy is also not Groovy — 8,442 lines with zero `def`, zero closures, zero GStrings and zero `@CompileStatic`, i.e. Java source with a `.groovy` extension paying dynamic-dispatch cost on the per-record hot path for literally no language benefit, which makes the entire gmavenplus stub/joint-compilation apparatus machinery for a cross-language dependency that does not exist. The correct resolution is not to optimize any of this yet: it is to make the build real, revive the 115 commented-out tests (one of which needs an 11-line fix to restore 45 passing round-trip tests), collapse to one language and one flatten/reconstruct core behind a facade, and only then optimize against a JMH baseline — because seven of the original performance claims were already refuted under adversarial verification, which is precisely what happens when you optimize without measurement.

## Top risks

1. Silent data corruption from the non-injective key encoding (arch/NP-002 + quality/NP-014 + quality/NP-034). Any field name containing the separator — `user_id`, `created_at`, `order_total`, i.e. most real snake_case schemas — collides or is split into the wrong nesting on reconstruct. Worse, the two flatteners resolve collisions in OPPOSITE directions: MapFlattener overwrites with the nested value while AvroSchemaFlattener keeps the top-level field, so the generated Spark StructType declares one field's provenance while the row data carries the other's. Neither side logs above TRACE. This is undetectable after the fact and it lands in the warehouse.

2. FileFinder is a security and liveness hazard on three axes at once. Its declared controls `validatePaths`, `allowedExtensions` and `maxFileSize` are never read (quality/NP-001), so any caller-influenced schema name yields arbitrary local file read via `../` — and `..`, `../..`, `../../..` are literally in the default search paths. It starts a non-daemon scheduled executor with no shutdown path (quality/NP-008), so every CLI and spark-submit driver that touches a schema hangs forever at exit. And it leaks `Files.walk` streams, `getResourceAsStream` probes and `FileFinder.findFile` handles (quality/NP-004/005/007), exhausting file descriptors in long-running drivers and failing in unrelated code.

3. The release and verification pipeline does not exist, so none of the other risks are observable. Zero CI runs on any commit or PR; checkstyle/PMD/SpotBugs are unreachable through every build path and are provably never downloaded; JaCoCo passes a 20% floor against 60.3% actual; `mvn deploy` runs without `-Prelease` so `gpg.skip` stays true and no signatures are produced; distributionManagement points at the decommissioned s01.oss.sonatype.org; and there are no tags, so no released artifact can be traced back to source. The first CI run will additionally hard-fail on Linux because the enforcer's `requireOS` rule silently collapses to `family=windows`.

4. One malformed or hostile `.avsc` file kills the driver. Avro explicitly permits self-referential named types, and neither Avro schema flattener has a depth or cycle guard: `AvroSchemaFlattener.collectRecordDefinitions` blows the stack (quality/NP-002), and `SchemaBasedMapConverter.flattenAvroSchema` tracks a depth counter it never checks, so `record Node { Node next }` loops forever building quadratically-growing key strings until OOM — a silent unkillable heap death rather than a fast failure (quality/NP-003). This is a trivially reachable DoS in a library whose stated job is loading schemas from disk, HDFS and S3.

5. Failures are systematically laundered into apparent successes. `JsonFlattenerConsolidator` catches every exception and returns `"{}"` (quality/NP-026, arch/NP-012), which `from_json` turns into an all-null row that passes the pipeline's own `_error IS NULL` success filter — so dropped records are counted in `successfulRecords`. A naive substring check discards valid records whose text merely contains `": undefined"`. Seven Spark UDFs swallow every exception into `null` (arch/NP-014). And `collectMetrics` references an `_error` column that FAIL_FAST and PERMISSIVE never create, so two of the four documented error-handling strategies throw AnalysisException at default settings (quality/NP-011). The quarantine contract the library advertises does not function.

# Phases

The ordering is the plan. Each phase exists because the next one is unsafe without it.

## Phase 0 — Make the build real and reproducible

**Goal.** Get a build that actually executes on a machine other than the maintainer's Windows workstation, on every push and PR, and that is not booby-trapped. No gates yet — just an honest, green, observable pipeline and the removal of the three landmines that would make every later fix look like the cause of a breakage.

**Why this order.** This must be first because it is the precondition for observation itself. Every one of the 200 findings is currently invisible to the project: nothing runs outside one workstation, so there is no mechanism by which any regression — or any fix — can be detected. Adding gates before adding a runner just moves the theatre; adding a runner before removing the `requireOS` landmine means the very first CI run dies at the `validate` phase on `ubuntu-latest` and the CI change gets blamed for it. Similarly, `lib/` must go before anything else touches git, because one careless `git add -A` writes 16MB of Groovy 5.0.0 jars into permanent history — unremovable without a rewrite of a published repo — and those jars also mean the IDE classpath (Groovy 5) disagrees with the Maven build (Groovy 4.0.21), so 'works locally, fails in CI' is already latent. Deleting the `development` activeByDefault profile also belongs here rather than in Phase 2, because leaving an activeByDefault profile that disables gates in place while you build gates is how the current situation happened.

**Deliverables.**

- `.github/workflows/ci.yml`: `mvn -B verify` on push and pull_request, JDK 17 + 21 matrix, `cache: maven`, `permissions: contents: read`, all actions pinned to full commit SHAs.
- `git mv maven-publish.yml .github/workflows/` so the release workflow is at least reachable (it is fixed properly in Phase 7).
- Delete the `<requireOS>` enforcer rule outright — it adds nothing for a pure-Java library and is currently `family=windows`.
- Delete the `development` activeByDefault profile. Delete the `java8` and `mixed-compilation` profiles (both dead; `java8` silently drops the enforcer floor from 17 to 8, `mixed-compilation` declares gmavenplus a third time).
- Delete gmavenplus from `<pluginManagement>`, keeping only the explicit `<build><plugins>` executions — currently 76 Groovy source units compile twice per build with racing stub generation.
- Delete `lib/`; add `lib/` and `*.jar` to `.gitignore`.
- `mvn wrapper:wrapper -Dmaven=3.9.10`; commit `mvnw`, `mvnw.cmd`, `.mvn/wrapper/`; CI and docs invoke `./mvnw`.
- Rename the `java.version` property to `maven.compiler.release` so it stops shadowing the JVM's own `java.version`; bound the enforcer to `[17,22)`.
- Fix surefire/failsafe include patterns to the extension-less form (`**/*Test`, `**/*Spec`) — five of the eleven current patterns are inert no-ops.
- Add the four missing `--add-opens` entries (`jdk.internal.ref`, `sun.security.krb5`) with `-XX:+IgnoreUnrecognizedVMOptions` first, so Spark off-heap and Hadoop UGI paths work when Phase 1 revives the Spark tests.
- `.gitattributes` with explicit binary/eol rules for `*.avro`, `*.parquet`, `*.jar`, `*.xlsx`, `*.avsc`, `*.json`, `*.sh`, `mvnw`.
- `.github/dependabot.yml` covering the `maven` and `github-actions` ecosystems, weekly.
- Branch protection on `main` requiring the CI status check.

**Exit criteria.** A pull request opened against `main` triggers a CI run that completes green on both ubuntu-latest/JDK17 and ubuntu-latest/JDK21; ~~the reactor log shows exactly one gmavenplus compile of the Groovy sources (not two)~~ — **moot since 2026-08-11**: gmavenplus and every `.groovy` source are gone, so there is no compile to count. Superseded by the Phase 5 language-purity criterion; `git status` is clean with no untracked `lib/`; `./mvnw -B verify` succeeds from a fresh clone on a machine with no prior `~/.m2`; and a deliberately-broken commit (e.g. a syntax error) is confirmed to fail the required status check and block merge.

## Phase 1 — Correctness net: revive the dead suite and install the ratcheting coverage gate

**Goal.** Turn 115 commented-out tests and 26 never-executing property tests into executing, merge-blocking signal; get the flatten→reconstruct identity property under test for JSON as well as Avro; take the Spark package off 0%; and replace the decorative 20% coverage floor with a ratchet that actually catches regressions.

**Why this order.** This is the hinge of the entire plan and it must precede every refactor and every optimization. Phases 4, 5 and 6 propose adding `@CompileStatic` to 8,442 lines of dynamic Groovy, renaming four files across a language boundary, decomposing a 2,979-line god class into seven, collapsing two parallel flatten implementations into one, and rewriting the recursion contract of `MapFlattener` — every one of those is a behaviour-preserving refactor whose only defence is a test suite. Today the suite has a hole shaped exactly like the work: the entire `io.github.pierce.spark` package is at 0.0% (2,995 instructions) and `JsonReconstructor.groovy` is 100% commented out in MAIN source, so the JSON round-trip identity — THE invariant for a flattener library — has zero coverage while Avro round-trip has 46 tests. Refactoring the reconstruction core with the reconstruction tests dark is not engineering, it is gambling. The cost/benefit here is also unusually good and it has been verified rather than assumed: resurrecting `JsonReconstructor` took exactly 11 mechanical line edits to go from 22/45 to 45/45 passing, and two of the three Spark test classes are pure comment-outs that already compile clean against current APIs. Coverage ratcheting belongs here and not later because a floor 40 points below actual is worse than no floor — it permits a two-thirds regression while the reactor log prints 'All coverage checks have been met'.

**Deliverables.**

- Uncomment `src/main/groovy/io/github/pierce/JsonReconstructor.groovy` and its test; apply the 11 verified edits (qualify the eight `case JSON:`-style enum labels; coerce three `','`/`'|'` char literals with `as char`); relocate the test to `src/test/groovy/io/github/pierce/` to match its declared package. Target: 45/45 green.
- Revive `NexusPiercerSparkPipelineTest` and `NexusPiercerPatternsTest` as-is (both compile clean). Revive `NexusPiercerFunctionsTest` after replacing its `@BeforeEach getOrCreate()`/`@AfterEach spark.stop()` lifecycle with the shared `SparkTestBase` — stopping the JVM-global SparkContext between tests is the classic source of 'SparkContext has been shutdown'. Restore or delete the truncated `SqlRegistrationTest` nested class. Validate on the CI JDK, not locally: the original comment-out may have been motivated by a real Windows/JDK-17 Spark failure.
- Revive `SchemaCompatibilityIntegrationTest` (2,488 lines, 35 tests) by repairing the ~12 mechanical sites left by the botched org.json→Jackson migration: `MAPPER.readTree()`→`createObjectNode()` typed as `ObjectNode`, `.put(name, List)`→`createArrayNode()` + `.set(...)`, `keySet()`→`fieldNames()`. Verify with `javac` before uncommenting.
- Replace `jqwik-api` (compile scope!) with the `net.jqwik:jqwik` aggregate at test scope; rename `TypeConverterProperties.java` → `TypeConverterPropertyTest.java`. Confirm a surefire report appears and the 26 properties actually execute and shrink.
- Move all 8 wall-clock/memory assertions behind `@Tag("perf")`, excluded from the default surefire run — including the two cache-warmup ratio assertions (`< firstLoadTime / 2`, `< firstTime / 10`) that JIT warmup alone can invert. Replace them with deterministic invariants (assert the cache returns the identical object reference, not that it is 10x faster).
- Delete or fix the two assertion-free tests and convert the 9 console-output 'diagnostic' tests to `@Tag("diagnostic")` or real assertions. Audit the 10 exception-swallowing catches. Route the 409 print statements through the existing logback-test.xml at debug.
- Delete the two tautological tests in `AvroSchemaFlattenerCompatibilityTest` that compare one implementation against itself, or convert them into golden-file tests.
- Introduce `src/test/resources/schemas/*.avsc` and `src/test/resources/golden/*.json` (expected flattened output and expected flattened Avro schema) behind one loader, replacing the 91 one-off inline schemas at the recurring shapes.
- Rewire JaCoCo: raise INSTRUCTION minimum to 0.58 as a ratchet, add a BRANCH counter limit, add a per-CLASS rule with an explicit `<excludes>` list so new zero-coverage classes fail rather than silently consuming the MISSEDCOUNT budget, move `report` to `verify`, and add `prepare-agent-integration`/`report-integration` so IT coverage appears in the report a human reads.
- Commit `coverage-baseline.properties`; CI fails a PR whose instruction coverage drops more than 0.5pp below baseline, and the merge job rewrites the baseline upward only.
- Add dedicated tests for the three classes with zero references anywhere in active test source: `AvroSchemaUtilWrapper`, `SchemaConversionUtil` (636 instructions, the largest untested non-Spark unit), `TimestampNanoConverter`.
- Add `org.pitest:pitest-maven` scoped to `io.github.pierce.*`, run nightly (not on PRs), publishing a mutation score — coverage percentage says nothing about assertion strength, and this suite demonstrably contains tests that no mutant can kill.

**Exit criteria.** `./mvnw -B verify` on CI runs ≥779 test methods with 0 failures; `io.github.pierce.spark` instruction coverage is >0% and JaCoCo reports ≥58% overall with the gate set at 58%; the 26 jqwik properties appear in a surefire report; a JSON flatten→reconstruct round-trip identity test executes and passes; a deliberately-introduced coverage drop of 2pp is confirmed to fail the PR; and zero wall-clock assertions remain in the default surefire run.

## Phase 2 — Quality gate that fails the build, supply-chain visibility, and truthful documentation

**Goal.** Convert five declared-but-never-executed static analysis plugins into merge-blocking gates with a recorded debt baseline that can only shrink; add CVE scanning and an SBOM; and eliminate the documentation lies that currently break every user who copies a README example.

**Why this order.** This follows Phase 1 rather than preceding it for one practical reason: turning Checkstyle, PMD and SpotBugs on for the first time against 19,860 lines that have never been linted will produce hundreds of violations at once. Without a green, trustworthy CI baseline (Phase 0) and a passing test suite (Phase 1), that flood is unattributable noise and the predictable response is to switch the gates back off — which is exactly the history recorded in this POM. It must precede Phases 4–6 because the static-analysis rules are themselves part of the anti-regression system for the refactors: a PMD rule banning `System.out`/`System.err`/`printStackTrace` in `src/main` is what stops arch/NP-012 and quality/NP-025 from regressing after they are fixed, and `enforceBytecodeVersion` plus `bannedDependencies` are what stop the dependency surface from re-expanding during the Phase 5 restructure. The documentation work is grouped here because it is the same category of defect — a declared contract with nothing behind it — and because four of six documented `NexusPiercerPatterns` methods simply do not exist, meaning the library's headline convenience API is fiction that every new user hits first.

**Deliverables.**

- Move checkstyle, PMD and SpotBugs out of the `quality` profile into `<build><plugins>` with explicit `<phase>verify</phase>` bindings and `check` goals; keep a single opt-out `-Dcheckstyle.skip=true` for local loops.
- Create the three missing config files the `quality` profile points at (a minimal `<FindBugsFilter/>` per SpotBugs filter, `<suppressions/>` for Checkstyle) so the plugins can actually load — today `mvn -Pquality verify` dies with MojoExecutionException before reporting a single violation, which is why the gates stayed off.
- Rebase `checkstyle.xml` on `google_checks.xml` and subtract, rather than the current three import rules at severity=warning; set `severity=error` for the honoured subset; flip `includeTestSourceDirectory` to true (29 test files are currently unexamined).
- Record existing violations in per-tool baseline files and add a ratchet step: CI fails if the violation count for any tool increases. New code is held to the full rule set from day one; legacy debt is visible and monotonically decreasing.
- PMD/Checkstyle rules banning `System.out`, `System.err`, `printStackTrace` and raw `catch (Exception)` in `src/main` — these are the regression guards for arch/NP-012, quality/NP-025 and quality/NP-020.
- `org.owasp:dependency-check-maven` at `verify` with `<failBuildOnCVSS>7</failBuildOnCVSS>` and an NVD API key; `org.cyclonedx:cyclonedx-maven-plugin` at `package` producing an `application` SBOM attached to the release.
- Bump `poi.version` to 5.4.0+ (CVE-2025-31672, currently compile scope so every consumer inherits it) and `logback.version` to 1.5.13+ (CVE-2024-12798/12801).
- Enforcer additions: `bannedDependencies` (`org.json:json`, `log4j:log4j`, `commons-collections:[,3.2.2)`), `requirePluginVersions` with `banSnapshots`, `banDuplicatePomDependencyVersions`, and extra-enforcer-rules `enforceBytecodeVersion` at `maxJdkVersion=17`.
- Remove the six zero-usage dependencies (including `jackson-dataformat-yaml` and `jackson-datatype-jsr310` at COMPILE scope, which drag snakeyaml onto every consumer), then flip `dependency:analyze` to `failOnWarning=true` with explicitly-documented `ignoredUnusedDeclaredDependency` entries for the genuine convergence pins.
- Root `README.md` (both current READMEs have spaces in their filenames, so GitHub renders no landing page at all): what the library is, Maven coordinates, one minimal working example, build instructions, links to the deep-dives. `git mv` the two existing files to `docs/`.
- Delete or implement the four documented-but-nonexistent `NexusPiercerPatterns` methods; fix `processStream`'s return type and the array-statistics default in `docs/API_SURFACE.md`; fix the `_avg` statistic that is never emitted, the nonexistent `create(...).build()` builder, and the `withRepartition(String)` snippet. Extract README snippets into a compiled examples source set that CI builds, so they cannot silently rot again.
- Governance set: `SECURITY.md` with GitHub private vulnerability reporting enabled, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `CHANGELOG.md` (Keep a Changelog, backfilled from 1.0.5), `.github/CODEOWNERS`, issue and PR templates.
- Regenerate `docs/MODULE_INDEX.md` mechanically (its counts understate the two largest files by 7x and 4x); repopulate `docs/CONCERNS.md` from this audit with honest severities and a `last verified against <sha>` line; reopen `docs/BACKLOG.md` BL-004 (marked COMPLETED, changes never made) and require a commit SHA on every future completion claim.
- Fix `.reuse/dep5` (dead Source URL, stanza for a nonexistent README, wrong inception year), migrate to `REUSE.toml`, add `reuse lint` to CI. Package `LICENSE` and `NOTICE` into `META-INF` and regenerate the third-party inventory with `license-maven-plugin:add-third-party`.
- Adopt Conventional Commits from this commit forward, enforced by a CI check on PR titles.

**Exit criteria.** `./mvnw -B verify` shows checkstyle, pmd and spotbugs each executing in the reactor log and each capable of failing the build (proven by a deliberately-introduced violation of each); dependency-check runs and the build has zero CVSS≥7 findings; a CycloneDX SBOM is produced; `mvn dependency:analyze` passes with `failOnWarning=true`; the GitHub repo page renders a README; and a compiled examples module builds every snippet published in the docs.

## Phase 3 — Measurement infrastructure: JMH module, standard corpora, and the performance gate

**Goal.** Stand up a JMH benchmark module that runs against the built artifact, a deterministic five-shape corpus that stresses different complexity dimensions, a committed baseline, and a CI gate that blocks merges on regression — validated by proving it detects a deliberately-injected regression.

**Why this order.** This precedes all optimization for a reason this project has already demonstrated empirically: of the original performance claims, seven were refuted under adversarial verification, and several of the survivors had their magnitudes corrected by an order of magnitude or more (the `Pattern.compile` finding was overstated ~25x; the `@CompileStatic` multiplier is realistically 1.5–3x, not the 3–10x cited from pre-invokedynamic Groovy). Optimizing on the basis of reasoning about bytecode is how those wrong numbers got written down in the first place. It also has to follow Phase 1, because a benchmark that measures incorrect behaviour fast is worthless — and it has to follow Phase 0/2, because the benchmark module changes the build topology and needs the enforcer, dependency and reproducibility rules already settled. Building the harness before the optimizations also lets the first optimization iteration be judged against a real number rather than a hoped-for one, which is what makes Phase 6 independently measurable at all.

**Deliverables.**

- Convert to a two-module reactor: `nexus-piercer-parent` (pom) → `nexus-piercer` (the published library, unchanged coordinates) + `nexus-piercer-benchmarks` (jar, `maven-deploy-plugin` skipped, never published). See benchmark_plan for why the benchmarks must not live in the library module.
- Deterministic corpus generator committed as code (seeded, no randomness at run time) plus the generated bytes checked in as golden fixtures under `benchmarks/corpora/`, so the corpus itself cannot drift between baseline and PR runs.
- `benchmarks/baseline.json` produced by the merge job on `main`, plus `benchmarks/waivers.yml` for deliberate, CODEOWNERS-reviewed throughput trades.
- A `.github/workflows/perf.yml` job implementing the gate described in benchmark_plan, plus the deterministic static-metric checks (invokedynamic count per class, hot-method bytecode size) which run on every PR because they have zero variance.
- A separate `@Threads(8)` contention benchmark set, because several findings (the `System.err` PrintStream monitor, the shared ObjectMapper, the ThreadLocal retention) have effects that a single-threaded JMH run cannot surface at all.
- A separate non-JMH Spark harness (`local[4]`, fixed input files, wall-clock and Spark accumulator assertions) for the pipeline findings, which are architectural double-execution problems rather than microbenchmark-visible ones.
- Harness self-validation: deliberately reintroduce a known regression (re-insert the hoisted `Pattern.compile` into `explodeFlattened`) on a scratch branch and confirm the gate fires; then reintroduce an allocation-only regression and confirm the `gc.alloc.rate.norm` gate fires. A gate that has never been observed to fail is indistinguishable from one that cannot.

**Exit criteria.** `java -jar nexus-piercer-benchmarks/target/benchmarks.jar -rf json` runs all five corpus shapes across flatten, consolidate and reconstruct paths on the CI runner and produces a committed `baseline.json`; run-to-run variance of `gc.alloc.rate.norm` is <1% and of throughput is <8% across three consecutive baseline runs on the same runner class; and both injected-regression drills (throughput and allocation) are confirmed to block a PR.

## Phase 4 — Eliminate the silent data-corruption class

**Goal.** Fix the defects that make the library produce plausible, wrong output with no error: the non-injective key encoding, collision handling that differs between schema and data, numeric wraparound, union branch loss, stale-cache metadata, unbounded recursion, and the resource leaks that hang or exhaust long-running drivers.

**Why this order.** This must precede the architectural convergence in Phase 5, not follow it, because you cannot merge two implementations until you have decided which behaviour is correct — and right now the two flatten stacks resolve the same key collision in opposite directions, so 'preserve existing behaviour' is not a well-defined instruction. Defining `FlattenedPath` with a real escaping scheme is the missing abstraction that the unification in Phase 5 is built on top of; doing the unification first would just pick one of two wrong encodings and enshrine it. It must also precede Phase 6, because there is no point optimizing a code path that is going to be rewritten to satisfy a different contract, and because several of these fixes (removing the exception-driven union cascade, adding depth guards) change the performance profile enough to invalidate a baseline taken after them. The resource leaks are grouped here rather than in Phase 0 because fixing them well means changing `FileFinder` from a static singleton with hidden global lifecycle into an instantiable `AutoCloseable` component — an API change, not a patch.

**Deliverables.**

- Introduce a `FlattenedPath` value type owning encoding and decoding, with an injective scheme (percent-escape the separator within segments, or better: carry the segment list structurally and render a String only at the Spark column-name boundary). Never pass raw Strings between flatten and reconstruct. Reconstruction consults the schema trie for longest-prefix matching instead of blind `String.split` — the `SchemaPathTrie` already holds every legal path and is currently dead code. Add a jqwik property round-tripping schemas whose field names contain the separator.
- One `FlattenedNaming` type owning the separator, array-index encoding and statistic suffixes, replacing four independent string-literal copies of the contract across `AvroSchemaFlattener`, `JsonFlattenerConsolidator`, `NexusPiercerFunctions` and `NexusPiercerPatterns`. Hoist `ArraySerializationFormat` to one top-level enum with each constant paired to its serializer AND deserializer, so a format cannot be added on only one side.
- One deterministic collision policy applied on both sides (disambiguate with a suffix, or fail with `DuplicateFlattenedFieldException` naming both source paths) — and at minimum WARN-level observability where today the loss is silent.
- `BigInteger.longValueExact()` with fallback to exact string form; default `preserveBigDecimalPrecision` to true; fix `IntegerConverter` to honour `allowNumericOverflow`/`allowPrecisionLoss` for BigInteger/BigDecimal, which strict mode currently bypasses entirely.
- Replace 'first branch that doesn't throw' union resolution with runtime-type dispatch (`GenericData.resolveUnion` semantics); catch only `TypeConversionException`, never `Exception`; pick one multi-branch union flattening policy and share one helper across all three code paths that currently disagree.
- Make `AvroSchemaFlattener` stateless: `flattenSchema` returns an immutable `FlattenedSchemaResult` (schema + arrayFields + terminalArrays + mapFieldPaths) and THAT is what gets cached, keyed on `SchemaNormalization.parsingFingerprint64` rather than `getFullName()`. This fixes the cache-hit-returns-empty-metadata bug, the schema-evolution collision, and the thread-safety race in one change.
- Depth and cycle guards on all three recursive schema walkers (`maxDepth` default 64 + `IdentityHashMap`/visited-fullName set), throwing a typed `SchemaTooDeepException`; a bounded `maxExplodedRecords` cap on the array cross-product.
- `FileFinder` becomes instantiable and `AutoCloseable`: allow-listed base directories with `toRealPath()`/`normalize()`/`startsWith` validation, enforced `allowedExtensions` and `maxFileSize`, `..` removed from default search paths, daemon threads plus a shutdown path, try-with-resources on `Files.walk`, `getResource` instead of `getResourceAsStream` for existence probes, negative-lookup memoization, and the broken `currentDepth` counter deleted.
- try-with-resources on `AvroSchemaLoader`'s three stream sites and the NDJSON reader; `StreamResult` becomes `AutoCloseable` with `onClose` cleanup; `toStream` stops closing the caller's stream; `toFile` writes to a temp file and moves atomically instead of truncating before validation.
- One exception hierarchy: `NexusPiercerException extends RuntimeException` with `FlattenException`, `ReconstructionException`, `SchemaException`, `FileResolutionException` beneath it, each carrying the field path or file name as structured data. Remove the phantom `throws IOException`. Replace `catch (Exception e) { print; return "{}" }` with a typed exception the pipeline's `ErrorHandling` strategy decides on — the decision belongs to the pipeline, not the flattener.
- Fix `collectMetrics`' unguarded `_error` reference so FAIL_FAST and PERMISSIVE stop throwing AnalysisException; implement or delete the never-read `errorHandlingMode`/`nullHandlingMode` config options.
- Correctness fixes with no architectural weight, batched: `java.sql.Timestamp` branch ordering (currently unreachable, silently dropping microseconds on every JDBC row); AUTO_DETECT timestamp precision rejecting ambiguous magnitudes instead of guessing; `toLowerCase(Locale.ROOT)` with collision detection in field lookup; UTF-8 explicit decoding of `.avsc`; `null.flattened` namespace; `Locale.ROOT` in the complexity-score format round-trip; `TypeConverterRegistry`'s dead null guard; `SafeConstructor` with explicit `LoaderOptions` for YAML; array/map truncation raised to WARN with a `failOnTruncation` option defaulting to true.
- Remove `Serializable` from `CachedSchema` and `FlattenTask`; make `AvroReconstructor` Serializable with `transient Schema` + `String schemaJson`; add a `SerializableAssertions` test round-tripping every type intended to enter a Spark closure, plus a closure-size assertion.
- Bound every cache (five in the reconstruct path, plus `CreateSparkStructFromAvroSchema` and the three converter caches) on Guava `CacheBuilder` or Caffeine with `maximumSize` + `expireAfterAccess`, keyed on content fingerprint rather than `System.identityHashCode`.

## Phase 5 — Architectural convergence: one language, one engine, one public API

**Goal.** Collapse three disjoint codebases into one coherent library: eliminate the accidental Java/Groovy split, unify the two flatten/reconstruct stacks onto a single engine behind a facade, resolve the converter island, and cut the public surface from 109 types to something a consumer can hold in their head.

## Phase 6 — Measured optimization campaign

**Goal.** Execute the ordered optimization iterations against the Phase 3 baseline, one independently-revertable commit at a time, each with a before/after JMH delta recorded in the PR.

**Why this order.** Last, because every prerequisite is now in place and none of them could have been retrofitted: the tests that prove each refactor is behaviour-preserving (Phase 1), the lint rules that stop the hot-path `System.err` calls from coming back (Phase 2), the harness that says whether a change helped and by how much (Phase 3), the settled semantics so the optimization is not preserving a bug (Phase 4), and one implementation instead of two so each fix is done once (Phase 5). # Benchmark plan

## Harness

JMH 1.37 in a dedicated `nexus-piercer-benchmarks` Maven module, NOT in the library module. This is the critical integration decision and it is forced by the dual compilation. JMH works by annotation processing: `jmh-generator-annprocess` reads `@Benchmark` methods and generates Java source for the harness classes, which then need a second javac pass. The library module currently runs gmavenplus through a five-execution lifecycle (add-sources → generate-stubs → compile-groovy, then add-test-sources → generate-test-stubs → compile-groovy-tests) interleaved with maven-compiler-plugin, and adding an annotation processor into that sequence means the processor runs against a source tree that includes generated Java stubs for Groovy classes — producing duplicate-class errors and non-deterministic ordering depending on which compile execution wins. Keeping benchmarks in a separate, pure-Java module with no gmavenplus at all sidesteps this entirely, and has a second benefit that matters more: the benchmarks module depends on the library ARTIFACT, so JMH measures the same compiled bytecode that ships to Maven Central — including whatever groovyc emitted — rather than a re-compilation with different flags. Reactor ordering guarantees the library is built first.

Concrete setup: parent POM `nexus-piercer-parent` (packaging pom) with modules `nexus-piercer` and `nexus-piercer-benchmarks`. The benchmarks module declares `org.openjdk.jmh:jmh-core:1.37` (compile) and `org.openjdk.jmh:jmh-generator-annprocess:1.37` (provided), sets `maven-compiler-plugin` `<annotationProcessorPaths>` explicitly (do not rely on classpath discovery — it silently no-ops under `-proc:none` defaults on newer JDKs), and uses `maven-shade-plugin` to build `target/benchmarks.jar` with `Main-Class: org.openjdk.jmh.Main` and the `ServicesResourceTransformer` (required — JMH's `META-INF/BenchmarkList` and `META-INF/CompilerHints` must be merged or the uber-jar finds zero benchmarks). `maven-deploy-plugin` and `maven-gpg-plugin` are skipped in this module; it is never published. Benchmarks are excluded from the default `mvn verify` via a `benchmarks` profile so ordinary builds stay fast.

Invocation in CI: `java -jar nexus-piercer-benchmarks/target/benchmarks.jar -rf json -rff results.json -prof gc -foe true`, with `-foe true` (fail-on-error) so a benchmark that throws is a hard CI failure rather than a silently-omitted result — this matters because several corpora deliberately exercise paths that currently throw. Spark-touching benchmarks reuse the POM's `spark.test.jvm.args` `--add-opens` block via `@Fork(jvmArgsAppend = ...)`.

Three things the JMH harness deliberately does NOT cover, each with its own mechanism because JMH is the wrong instrument: (1) Spark pipeline findings (SCHEMA-01/02/03) are double-execution and plan-shape problems measured by a separate `local[4]` integration harness asserting on Spark accumulators and stage counts, not ns/op. (2) Multi-threaded contention (the `System.err` PrintStream monitor, shared caches, ThreadLocal retention) needs a `@Threads(8)` / `@State(Scope.Benchmark)` benchmark set — a single-threaded run cannot surface a lock. (3) Deterministic static metrics (invokedynamic count, hot-method bytecode size) are extracted by parsing `javap -c -p` output in an ordinary JUnit test, because they have zero variance and therefore deserve a tight gate that benchmark noise would otherwise swamp.

## Standard datasets

- wide-flat — 1 record, 1,000 scalar fields at depth 1, mixed String/long/double/boolean, ~45 KB serialized. Stresses everything whose cost is linear in key count and independent of structure: the per-key regex `find()` in `consolidateFlattened` (JFLAT-01), default-sized LinkedHashMaps rehashing ~5 times (JFLAT-16), the four parallel per-field maps in `SchemaBasedMapConverter`'s constructor (SCHEMA-26), and the `get_json_object` OR-chain that Spark builds one branch per numeric column (SCHEMA-01). This is the corpus where a fix that halves per-key cost shows up cleanly with no structural confound.

- deep-narrow — depth 24, exactly one field per level, 1 leaf value, ~2 KB serialized. Deliberately tiny so that anything measurable is depth-driven, not size-driven. This is the discriminating corpus for the two quadratic-in-depth findings: MapFlattener's per-node throwaway LinkedHashMap that `putAll`s up the recursion so a leaf at depth d is re-inserted ~2d times (JFLAT-04 — note there are two maps per level, not one, so the leaf is copied twice per level), the `buildKey` prefix rebuild (JFLAT-10), and `isArrayFieldPattern`'s O(d²) character copying via `String.join` + `Arrays.copyOfRange` (RECON-04). Also the natural home for the depth-guard regression tests from Phase 4. Add a depth-64 variant to sit exactly at the new `maxDepth` boundary.

- array-heavy — 1 record with 20 scalar array fields × 500 elements (10 numeric-typed, 10 string-typed) plus 5 arrays-of-records × 100 elements × 8 fields, ~600 KB serialized. This is the allocation-rate headline corpus. The 10,000 scalar elements in string-typed arrays drive exactly 10,000 `NumberFormatException` constructions per record through `determineArrayType`'s no-early-exit type detection (JFLAT-05, measured 418.6 ns/elem vs 1.3 ns for a char scan); the five-pass `processArrayValues` (JFLAT-15) touches every element ~5 times; `serializeArray` copies the whole list to apply a no-op transform (JFLAT-17); `GAvroSchemaFlattener` parses every serialized array and immediately re-serializes it to the same string (RECON-09); and `SerializedArrayConverter` boxes every primitive element through `java.lang.reflect.Array` (SCHEMA-24). Expect this corpus to show the largest `gc.alloc.rate.norm` reduction of the five.

- union-nullable-heavy — 1 record, 200 fields, every field a 3-branch union `["null", T, U]`, with the value distribution deliberately skewed so 70% of populated fields match the LAST branch and 15% are null, ~12 KB serialized. Includes a date column in US `M/d/yyyy` form (not ISO-8601) and a `["null","long","string"]` union carrying non-numeric strings. This corpus exists to make exception-driven control flow visible: SCHEMA-09's cascade constructs up to three stack-filling exceptions per value before reaching the right branch (the long branch alone throws a NumberFormatException from `Long.parseLong`, a second from `new BigInteger`, then a TypeConversionException whose `formatMessage` calls `String.format` and `value.toString()`), and SCHEMA-07's DateConverter throws three `DateTimeParseException`s per value for non-ISO dates. Note the honest caveat: an all-ISO-8601 corpus would show near-zero cost here, which is precisely why the skew is deliberate and documented — this corpus measures the worst realistic case, not the average one, and both must be reported.

- mixed-production — the headline corpus, 1,000 records per operation. 250 fields, nesting depth 4, 12 array fields with a realistic size distribution (mean 30 elements, p50 8, p99 400), 40% nullable, a mix of timestamps/decimals/UUIDs/enums, ~35 KB per record (~35 MB per op-batch). Two properties are non-negotiable in the generator: field names are snake_case and therefore CONTAIN the separator (`user_id`, `created_at`, `order_total`), which makes this corpus a live regression test for the NP-002 injectivity fix as well as a performance benchmark; and the record shape is fixed by seed so baseline and PR measure identical bytes. Reported as both `Mode.Throughput` (records/s, the number quoted externally) and `Mode.SampleTime` p50/p99/p999 (Spark task skew is driven by the tail, not the mean).

- adversarial — NOT gated on performance, run nightly with correctness assertions only: a self-referential Avro schema, a 10,000-element single array, three explosion paths of 1,000 elements each (the 10⁹ cross-product case), field names that collide under the separator, a 5 MB single record, and a `.avsc` with `../` in its name. Each asserts bounded, typed failure within a time and memory budget — these are the DoS findings from Phase 4, and their regression test is 'fails fast and correctly', not 'runs fast'.

## Metrics

- Throughput (`Mode.Throughput`, ops/s) at two granularities: per-record for latency-shaped paths and per-1,000-record batch for the mixed-production corpus. The externally-quoted number.

- Average time (`Mode.AverageTime`, ns/op) for single-record flatten, consolidate, and reconstruct — the cleanest signal for the per-key and per-depth findings.

- Tail latency (`Mode.SampleTime`, p50/p99/p999). Included because Spark job wall-clock is set by the slowest task, so a change that improves the mean while worsening p999 is a regression in production even though it looks like a win in ops/s.

- `gc.alloc.rate.norm` from `-prof gc` — bytes allocated per operation. THE primary gate metric, because most surviving findings here are allocation-driven (throwaway LinkedHashMaps, exception objects, Pattern/Matcher pairs, boxed Integers, Groovy Closures, intermediate Strings) and because it is a near-deterministic counter derived from thread-allocation accounting rather than a timing measurement. It does not move with runner load, which means it can carry a 2% gate where throughput needs 10%.

- `gc.count` and `gc.time` per operation from `-prof gc` — catches promotion-rate changes that `alloc.rate.norm` alone misses (e.g. a change that allocates the same bytes but keeps them alive longer).

- `-prof comp` JIT compilation time, as an indirect read on the RECON-08 inlining problem: five hot methods are 3–6x over the 325-byte `FreqInlineSize` threshold, and splitting them should show up as changed compilation behaviour before it shows up as throughput.

- Deterministic static metric — `invokedynamic` count per class in `io.github.pierce.**`, extracted from `javap -c -p`. Currently 677 in `MapFlattener.class` and 1,773 plus 257 `ScriptBytecodeAdapter` calls in `AvroReconstructor.class`. Must reach 0 after Phase 5 and stay there. Zero variance, so it gets an absolute gate.

- Deterministic static metric — bytecode size of every method annotated as hot-path, gated at <325 bytes. Directly enforces RECON-08 rather than hoping the JIT effect shows through benchmark noise.

- Deterministic runtime counter — exceptions constructed per operation, captured via a JFR `jdk.JavaExceptionThrow` event count on the benchmark fork. Makes the JFLAT-05, SCHEMA-07 and SCHEMA-09 exception-driven-control-flow findings gateable at near-zero variance, which is much stronger than trying to see 10,000 `fillInStackTrace` calls in a wall-clock number.

- Serialized closure size in bytes for every object entering a Spark closure (asserted in a JUnit test, not JMH) — the regression guard for arch/NP-008, where the UDF lambda currently captures `this` and ships the SparkSession plus all schema analysis metadata to every task.

## Regression gate

Two-tier, because the metrics have radically different noise characteristics and applying one threshold to both either produces false failures or lets real regressions through.

TIER 1 — deterministic metrics, run on EVERY pull request, no retries, absolute thresholds. (a) `gc.alloc.rate.norm`: block if any gated benchmark allocates >2% more bytes/op than baseline. (b) `invokedynamic` count in `io.github.pierce.**`: block on any increase above the recorded value (target 0 post-Phase-5). (c) Hot-path method bytecode size: block if any method on the annotated hot path exceeds 325 bytes. (d) Exceptions constructed per operation: block on any increase above baseline. (e) Serialized Spark closure size: block if any closure exceeds 8 KB. These are counters, not timings — they do not vary with runner load, so a 2% band is real signal and a failure here is never retried.

TIER 2 — throughput, run on the merge queue and nightly rather than on every PR (a GitHub-hosted shared-vCPU runner cannot produce a trustworthy timing measurement in PR-latency budget). Configuration for a gating run: `-f 3 -wi 5 -i 10 -w 1s -r 1s`, three forks to capture JVM-to-JVM variance rather than only within-JVM variance. The gate is defined on confidence intervals, not point estimates: block a benchmark only when BOTH conditions hold — the 99.9% confidence intervals of the PR run and the baseline run are DISJOINT, AND the PR point estimate is more than 10% worse. Overlapping intervals are never a failure regardless of the point estimate, which is what eliminates the false-failure mode. Additionally block if the geometric mean across the whole gated suite regresses more than 5% with disjoint intervals — this catches the death-by-a-thousand-cuts case where every benchmark degrades 4% and none individually trips.

Noise control beyond the CI band: (i) baseline and PR must be measured on the same runner class, and the baseline is regenerated only by the merge job on `main`, never on a fork; (ii) three consecutive baseline runs must show <8% throughput variance and <1% `alloc.rate.norm` variance before the gate is armed at all — if the runner cannot hit that, the gate moves to a self-hosted pinned runner rather than being loosened; (iii) a Tier-2 failure triggers exactly one automatic rerun, and only two consecutive failures block, which converts a transient noisy-neighbour event into a delay rather than a false rejection; (iv) Tier-1 failures never retry.

Escape hatch, deliberately narrow: a PR that intentionally trades throughput (e.g. Phase 4's injective key encoding is expected to cost something relative to a blind `String.split`) must add an entry to `benchmarks/waivers.yml` naming the benchmark, the accepted regression percentage, an expiry date, and the justification. Waivers require CODEOWNERS approval and appear in the CI summary, so accepted regressions are visible and time-boxed rather than silently absorbed. An expired waiver fails the build.

The gate is not considered live until it has been observed to fail: Phase 3 requires two drills — reintroducing a hoisted `Pattern.compile` (Tier 2) and reintroducing a per-node map allocation (Tier 1) — each confirmed to block a PR. An untested gate is indistinguishable from a disabled one, which is the exact failure mode this repository already exhibits with its 20% coverage floor and its never-downloaded static analysis plugins.

Hoist the three in-loop `Pattern.compile` sites (`explodeFlattened`, `processGroupedValues`, `shouldKeepAsArrayElements`) into constructor-computed arrays, and switch `arrayField.replaceAll(...)` to the already-declared static `ARRAY_INDEX_STRIP_PATTERN`. Hoist the invariant normalized-array-field-set computation out of the per-group loop entirely. Add a constructor-cached `arrayDelimiterPattern`. Size the three output LinkedHashMaps from known input. Delete the two pre-parse `indexOf` scans and the dead `MALFORMED_JSON_PATTERN`/`flattenSingleValue`/`batchSize` members.

**Expected gain.** array-heavy corpus: 1.6–3.0x throughput and a 40–60% reduction in `gc.alloc.rate.norm`, driven almost entirely by removing ~10,000 `NumberFormatException` constructions per record (measured 418.6 ns/elem vs 1.3 ns for the char scan — a 322x ratio on the isolated operation). wide-flat corpus: 1.2–1.6x, from removing the per-key backtracking `find()` (measured 8,261 ns vs 7.7 ns per 68-char key). Explicit honesty about why the end-to-end range is far below the microbenchmark ratios: Jackson parse and map construction dominate the record path, so a 322x improvement on one operation that occupies perhaps 20–35% of the profile yields roughly 1.5–2.5x overall — not 322x. The `Pattern.compile` hoists are worth much less than originally claimed: adversarial measurement put the realistic saving at ~8x on the affected inner-loop pass rather than 100x, and only ~28% of `processGroupedValues`' cost is the avoidable compile (the rest is Matcher and StringBuilder allocation that switching to a static Pattern does not remove). Expect 0.05–0.15x from the hoists alone; the exception elimination is where this iteration earns its keep.

**Risk.** Lowest in the campaign. Single language, single file, no API change, no cross-module effect, and the hand-rolled `looksNumeric` scan is the only place where a behavioural difference could hide — it must accept exactly what `Double.parseDouble` accepts (including leading `+`, exponent forms, and `Infinity`/`NaN` literals, which the current code accepts by not throwing). Cover that with a jqwik property asserting `looksNumeric(s) == canParse(s)` over generated strings before merging. Everything else is a mechanical hoist.

**Validation.** JMH delta on array-heavy and wide-flat corpora with disjoint 99.9% CIs; JFR exception-count metric drops from ~10,000/op to <10 on array-heavy; `gc.alloc.rate.norm` reduction confirmed at Tier-1 tolerance; full Phase 1 suite green including the revived `SchemaCompatibilityIntegrationTest` (35 tests specifically covering array statistics on/off and numeric edge cases); jqwik `looksNumeric` equivalence property passes.

## Iteration 2 — Per-record → per-schema hoists in the reconstruction path

**Targets:** `perf-avro/RECON-02`, `perf-avro/RECON-03`, `perf-avro/RECON-13`, `perf-avro/RECON-14`, `perf-avro/RECON-15`, `perf-avro/RECON-18`, `perf-avro/RECON-19`, `perf-avro/RECON-20`

**Change.** Six independent hoists, each a few lines. (a) Stop recomputing `SchemaNormalization.parsingFingerprint64()` per record: key the schema cache on the `Schema` instance itself (Avro memoizes its own hashCode), or better expose a `prepare(Schema)` returning a reusable per-partition plan. (b) Replace `key.split(Pattern.quote(separator))` — which forces a fresh `Pattern.compile` per flat key per record — with a hand-rolled `indexOf`-based splitter correct for both single- and double-character separators, and memoize the split per distinct flat key in the per-schema cache entry, since the key set is identical across every record in a batch. (c) Hoist the anonymous `TypeReference<List<Object>>` to a static constant at all four sites. (d) Delete the structurally-dead `ARRAY_PARSE_CACHE` (cleared per record and keyed by a name unique within a record — a provable 0% hit rate plus a ThreadLocal retention surface). (e) `LinkedList` → `ArrayDeque` for the BFS queue in `genericRecordToMap`. (f) Replace `getClass().getSimpleName().equals("NullObject")` per array element with an identity comparison against the `NullObject` singleton, and replace the copy-pasted `looksLikeJson` heuristic (five `String.contains` scans plus a recompiled regex) with a single first-non-space-character dispatch.

**Expected gain.** Reconstruct path on mixed-production: 1.8–3.5x. The fingerprint hoist alone is the highest-confidence single win in the entire campaign — it converts an O(schema-size) canonical-form string serialization plus Rabin hash executed once per record into an O(1) hashCode lookup, and for a 250-field schema that canonical form is several KB constructed 1,000 times per op-batch purely to look up a cache entry that never changes. The split hoist removes on the order of 250,000 `Pattern.compile` calls per op-batch. Both are pure waste with no semantic content, which is why confidence is high. The remaining four are small individually (each worth low single-digit percent) but collectively meaningful on `gc.alloc.rate.norm` for the array-heavy corpus.

**Risk.** Low, with one genuine trap: switching the cache key from a content fingerprint to object identity/hashCode changes cache semantics. Avro's `Schema.hashCode()` is content-based and memoized so this is safe for correctness, but two structurally-identical schemas parsed separately will now hit the same entry where previously they also did (fingerprint) — no change — while a mutated Schema would now be a stale hit. Avro Schemas are effectively immutable after parsing, so this is acceptable, but it must be documented and covered by a test that parses the same `.avsc` twice and asserts one cache entry. The hand-rolled splitter needs a property test against `Pattern.quote(separator)`-based splitting across generated keys, particularly for empty segments and trailing separators where `String.split`'s limit-0 behaviour drops trailing empties.

**Validation.** JMH delta on the reconstruct benchmarks across all five corpora; the 46 Avro round-trip tests plus the 45 revived JSON round-trip tests green; splitter equivalence property over ≥10,000 generated keys including separator-adjacent edge cases; cache-identity test confirming one entry for two parses of the same schema.

## Iteration 3 — Type-tag union dispatch and formatter hoisting in the converter layer

**Targets:** `perf-schema/SCHEMA-07`, `perf-schema/SCHEMA-09`, `perf-schema/SCHEMA-12`, `perf-schema/SCHEMA-14`, `perf-schema/SCHEMA-25`, `perf-schema/SCHEMA-26`

**Change.** Replace 'first branch that does not throw' union resolution with a small switch on the runtime type of the value (`Number`/`CharSequence`/`ByteBuffer`/`Map`/`Collection`/`Boolean`) matched against the branch schemas, following `GenericData.resolveUnion` semantics, falling back to trial conversion only for genuinely ambiguous cases; catch only `TypeConversionException`, never `Exception`; delete the dead `errors` ArrayList that `AvroSchemaConverter` accumulates per value and never reads. Hoist every `DateTimeFormatter.ofPattern` call to a static final field and replace the four-deep exception cascade with cheap shape discrimination (length, presence of `/`, `-`, `T`, `:`, `Z`) plus per-column memoization of the format that succeeded for the first non-null value. Add a `ConversionConfig.DEFAULT` singleton (the class is immutable; `defaults()` currently allocates a Builder plus a config with ~40 field stores on every call, including on cache-hit paths). Elide `StructConverter`'s unconditional defensive map copy when the first key is already a `String`. Collapse the four parallel per-field LinkedHashMaps in `SchemaBasedMapConverter`'s constructor into one `FieldPlan` record plus one lowercase index, and drop the defensive copy of a map the caller does not retain. Replace `parseNumber`'s `toLowerCase().contains("e")` with a two-`indexOf` scan.

**Expected gain.** union-nullable-heavy corpus: 3–8x, the largest single-corpus factor in the campaign, because that corpus is deliberately constructed to make exception-driven control flow dominant — a `["null","long","string"]` union carrying non-numeric strings currently constructs three stack-filling exceptions per value (NumberFormatException from `Long.parseLong`, a second from `new BigInteger`, then a TypeConversionException whose `formatMessage` calls `String.format` and `value.toString()`), and a US-format date column throws three `DateTimeParseException`s per value. Inside a Spark task with a 60–100 frame stack, each `fillInStackTrace` is far more expensive than in an isolated microbenchmark, so the corpus number is a floor for production, not a ceiling. Blunt caveat: on the mixed-production corpus the gain is much smaller, 1.05–1.3x, and on an all-ISO-8601, single-branch-dominant workload it approaches zero. Both numbers must be published — quoting only the union-heavy figure would be exactly the kind of unverified performance claim this project has already been caught making seven times.

**Risk.** Medium, and the highest-risk item so far, because it changes observable behaviour rather than just cost. Type-tag dispatch will select a DIFFERENT union branch than declaration-order trial conversion in at least one real case: for `["string","long"]` the value `12345L` currently becomes the String `"12345"` and will now correctly become a long. That is a bug fix, but it is a bug fix that changes column types downstream, so it must ship in the Phase 4 breaking release with an explicit CHANGELOG entry — not slipped in as an optimization. The per-column date-format memoization is also a behaviour change for heterogeneous columns (mixed `M/d/yyyy` and ISO in one column will now try the memoized format first and fall back, which is correct but reorders which format wins for genuinely ambiguous values like `01/02/2024`); require an explicit configured format for such columns rather than guessing.

**Validation.** JMH delta on union-nullable-heavy AND mixed-production, both reported; JFR exception-count drops from ~600/op to <20 on the union corpus; the 26 revived jqwik converter properties green (this is precisely what property-based testing is for, and it is the main reason TA-003 was scheduled into Phase 1); a targeted test matrix asserting the selected branch for every combination of union shape and runtime value type; explicit CHANGELOG entry for the branch-selection change.

## Iteration 4 — Eliminate dynamic dispatch — the Groovy-to-Java port lands as a measured change

**Targets:** `perf-flatten/JFLAT-03`, `perf-avro/RECON-01`, `perf-avro/RECON-07`, `perf-avro/RECON-10`, `perf-avro/RECON-12`, `arch/NP-004`

**Change.** Phase 5 renames the four live `.groovy` files to `.java` and deletes gmavenplus; this iteration is the measurement of that change against the baseline, plus the follow-on cleanups that only become possible once the compiler is javac: replace the `isNullable` Stream-plus-Closure with the two-iteration loop already present elsewhere in the same file, replace the wildcard static enum import so constants resolve as `getstatic`, and let the `switch` statements compile to real `tableswitch` on enum ordinal instead of linear `ScriptBytecodeAdapter.isCase` chains (70 such sites in AvroReconstructor, 47 in GAvroSchemaFlattener). Make `PathNode` fields final and its `children` map lazily allocated so leaf nodes cost one object instead of two.

**Expected gain.** 1.5–3.0x across all corpora on the Groovy-originated paths, and I want to be explicit that this is a deliberate correction downward from the 3–10x figure in the original findings. That figure is the pre-invokedynamic Groovy number; this build sets `<invokeDynamic>true</invokeDynamic>`, so monomorphic call sites already stabilize into a GuardWithTest MethodHandle chain that the JIT inlines tolerably well. The adversarial verification also undercut the 'megamorphic dispatch' argument: most of the 28 call sites in `normalizePrimitive` sit immediately after an explicit cast, so each sees one receiver type. What is unambiguously real and verified by `javap`: 677 `invokedynamic` in `MapFlattener.class`, 1,773 plus 257 `ScriptBytecodeAdapter` calls in `AvroReconstructor.class`, `new LinkedHashMap<>()` compiling to `invokedynamic #5:init`, and `buildKey`'s `prefix + separator + key` compiling to two separate unfused dynamic `plus` calls plus `compareEqual` and `booleanUnbox`. Removing all of that is worth a solid constant factor; claiming an order of magnitude would be repeating the project's existing mistake. Secondary and certain: the published artifact loses two runtime dependencies and the build loses a compiler.

**Risk.** Medium-high, and the highest-consequence iteration in the campaign — it touches 8,442 lines at once. The mitigating fact, which I verified directly rather than taking on trust, is that there is no cross-language boundary to break: the only mention of a Java main class anywhere in the Groovy tree is a Javadoc comment at `GAvroSchemaFlattener.groovy:27`, and there are zero references in the other direction. The real hazards are semantic differences javac will not flag: Groovy truthiness (`if (someMap)` means non-empty, `if (someObject)` means non-null) versus Java's boolean requirement, implicit `toString()` coercion, `==` meaning `equals()` in Groovy, and `def`-free but still dynamically-resolved property access. Every one of those either fails to compile under javac (safe) or compiles to different semantics (dangerous) — the `==` case is the one to hunt for explicitly with a targeted grep before the port. This iteration must not be combined with any other change in the same PR, and it must be revertable as a single commit.

**Validation.** `javap -c -p` reports 0 `invokedynamic` and 0 `ScriptBytecodeAdapter` across `io.github.pierce.**` (Tier-1 deterministic gate); JMH delta on all five corpora; the entire Phase 1 suite green including all 46 Avro and 45 JSON round-trip tests and the 26 jqwik properties; a pre-port grep audit of every `==` comparison in the four files with a written disposition for each; nightly PIT mutation score not regressed.

## Iteration 5 — Single-accumulator recursion in the flatten core

**Targets:** `perf-flatten/JFLAT-04`, `perf-flatten/JFLAT-10`, `perf-flatten/JFLAT-11`, `perf-flatten/JFLAT-12`, `perf-flatten/JFLAT-13`, `perf-flatten/JFLAT-23`

**Change.** Thread one output map and one StringBuilder through the entire flatten recursion instead of allocating and merging per node. Change `flattenObject`/`flattenValue`/`flattenList`/`flattenArray` to `void`-returning methods taking `(source, StringBuilder prefix, int depth, Map<String,Object> out)`, with leaves writing directly to `out`; allocate the single output map once in `flatten()` with an estimated initial capacity; append/`setLength(mark)` on the StringBuilder for descent and return. Replace the `Set<Integer>`/`Deque<Integer>` circular-reference tracking (five `identityHashCode` boxings per node, plus removal by linear scan) with an int-keyed open-addressing set and an `int[]` stack using `pop()`, which is safe because the `finally` block guarantees LIFO exit order. Hoist the three SNAKE_CASE `Pattern.compile` calls out of `applyNamingStrategy` and fold the naming transform into the emit path so the result map is not copied a second time. Precompile wildcard exclude patterns in the constructor so `matchesPattern` stops allocating a Closure on every cache hit. Make `ObjectMapper` static final.

**Expected gain.** deep-narrow corpus: 2.5–4.0x with a 60–80% `gc.alloc.rate.norm` reduction — this is the corpus the refactor is aimed at, and the isolated measurement (124.3 µs vs 31.0 µs for a depth-6/972-leaf tree, 4.0x) was taken in plain Java before Groovy overhead, so post-iteration-4 it should be close to that figure. mixed-production (depth 4): 1.3–1.8x, since the copy cost is linear in depth and depth 4 is shallow. Worth noting the finding was if anything understated: there are TWO throwaway maps per recursion level, not one — `flattenValue` allocates a LinkedHashMap and `putAll`s `flattenObject`'s result into it, which `flattenObject` then `putAll`s into its own — so a leaf at depth d is re-inserted ~2d times. One caveat on the ceiling: the '0 allocations for interior nodes' target is not reachable by threading a StringBuilder alone, because `shouldIncludePath(newKey)` is called on every interior key and would also need to accept a CharSequence.

**Risk.** Medium. This rewrites the recursion contract of the class that the entire library's semantics rest on, and it changes methods from value-returning to accumulator-mutating, which means an early return or exception mid-recursion now leaves partial state in `out` where previously it discarded a local map. Every `return` and every `catch` in the four methods must be audited for that. The `StringBuilder` `setLength` discipline is also easy to get subtly wrong — a missed reset produces keys with stale prefixes, which is exactly the failure mode the round-trip tests catch but only if the corrupted key still parses. Ship it alone, after iteration 4 so it is written in Java where javac can check it, and never in the same PR as a semantic change.

**Validation.** JMH delta on deep-narrow and mixed-production; `gc.alloc.rate.norm` reduction at Tier-1 tolerance on deep-narrow; the flatten→reconstruct identity property over ≥10,000 generated documents (this is the single most important gate for this iteration and the direct reason TA-001 and TA-003 were scheduled into Phase 1); explicit test for a mid-recursion exception leaving no partial output visible to the caller; the depth-64 boundary corpus producing identical output before and after.

## Iteration 6 — Spark pipeline: stop executing the job twice and stop re-parsing per column

**Targets:** `perf-schema/SCHEMA-01`, `perf-schema/SCHEMA-02`, `perf-schema/SCHEMA-03`, `perf-schema/SCHEMA-23`, `quality/NP-039`, `arch/NP-008`

**Change.** Four changes to the Spark integration, measured on the `local[4]` harness rather than JMH. (a) Stop calling `cache()` then `unpersist()` before the returned lazy Dataset is consumed — either return the cached Dataset with an explicit `release()` on `ProcessingResult`, or drop `cache()` entirely and derive metrics from Spark accumulators inside the UDF or an `observe()` listener, which costs nothing extra. (b) Replace the per-numeric-column `get_json_object` OR-chain with a single type-compatibility check performed once per row inside the flatten UDF, returning a boolean alongside the flattened JSON in a struct. (c) Hoist one `static final` flattener per distinct configuration out of the seven UDF lambdas, add a flattener overload returning the flattened `Map` so the extraction UDFs stop serializing K entries to JSON and re-parsing them to read one key, and precompute the underscored array path once instead of per row. (d) Hoist `broadcast.getValue()` and the field/DataType array out of the row loop, and replace the boxing `extractJsonNodeValue`/`isTypeCompatible` pair with a direct `JsonNode`-vs-`DataType` check.

**Expected gain.** The largest absolute production impact in the campaign and the hardest to state as a single number. (a) is close to a 2x end-to-end win whenever metrics are enabled, which is the default — the expensive part of the job currently executes exactly twice, since `collectMetrics` is the only action that materializes the cache and `unpersist()` discards it before the caller touches `successDataset`. (b) scales with column count: on the wide-flat 1,000-field shape it is dramatic, on a 20-column schema it is marginal; the adversarial correction is important here — the re-parse happens once per numeric column whose parsed value is NULL on that row, so it is 0 for a fully-populated row and F_num only in the worst case, meaning the realistic mixed-production gain is 1.2–2x rather than the 120x the naive reading suggests. (c) removes a serialize-plus-reparse of the entire document per row per UDF invocation — 1.5–4x on UDF-heavy queries. Honest framing: these numbers are wall-clock on a `local[4]` harness with fixed inputs and will not reproduce as clean factors on a real cluster where shuffle and IO dominate.

**Risk.** Medium, concentrated in (a). Changing cache lifetime changes memory behaviour on real clusters in ways a `local[4]` harness cannot predict — returning a cached Dataset that the caller never releases converts a wasted materialization into a storage-memory leak, which is arguably worse. Prefer the accumulator/`observe()` route over returning a cached Dataset for exactly that reason. (b) also changes where validation failures surface, which interacts directly with the Phase 4 `ErrorHandling` fixes and must not be attempted before those land. (c) makes the flattener a shared instance across executor threads, which is only safe because Phase 4 already fixed the never-removed ThreadLocal — sequencing matters.

**Validation.** `local[4]` harness asserting on Spark accumulator counts and stage/job counts, not just wall-clock: the flatten UDF invocation count must equal the input row count exactly once, which is the direct machine-checkable statement of 'the job no longer runs twice'; physical-plan assertions confirming the `get_json_object` OR-chain is gone; the revived `NexusPiercerSparkPipelineTest`, `NexusPiercerFunctionsTest` and `NexusPiercerPatternsTest` green; closure-size assertion under 8 KB.

**Change.** Fuse `processArrayValues`' five passes over the same values into one loop accumulating the joined value into a StringBuilder while tracking min/max/total length, feeding a HashSet for distinct count and updating the numeric/boolean flags inline. Make `serializeArray` skip its whole-list copy when no element actually changes (elements are already normalized upstream by `normalizePrimitive`), and replace its two per-format Closures with one StringBuilder loop parameterized by delimiter. Short-circuit `GAvroSchemaFlattener`'s parse-then-reserialize when every element already satisfies the declared element type. Replace the `from(InputStream)`/`from(Reader)` line-joining slurp with `readValue(inputStream, MAP_TYPE_REF)` — which also fixes the correctness bug where stripped newlines turn a `//` comment into a comment over the rest of the document. **Validation.** JMH delta on array-heavy; peak-RSS and max-document-size measurement for the streaming change on a purpose-built 100 MB input; golden-file comparison confirming byte-identical serialized output before and after for all five corpora (this is what the Phase 1 golden datasets exist for); the 35 revived `SchemaCompatibilityIntegrationTest` tests, which cover arrays at and beyond `maxArraySize` specifically.

## Iteration 8 — Content-keyed bounded caches and filesystem lookup memoization

**Targets:** `perf-schema/SCHEMA-11`, `perf-schema/SCHEMA-15`, `perf-schema/SCHEMA-16`, `perf-schema/SCHEMA-17`, `perf-schema/SCHEMA-18`, `perf-schema/SCHEMA-19`, `perf-schema/SCHEMA-20`, `perf-schema/SCHEMA-22`

**Change.** Phase 4 already made these caches correct and bounded; this iteration measures the throughput consequence and adds the lookup-side work. Confirm all eight caches are keyed on content (Avro `Schema.hashCode()` is memoized and content-based; Iceberg `Schema.asStruct().hashCode()`) rather than `System.identityHashCode`, backed by Caffeine or Guava `CacheBuilder` with `maximumSize` and `expireAfterAccess`, with no per-lookup key-String concatenation. Move Caffeine from `dependencyManagement` into real `<dependencies>` or standardize on the Guava `CacheBuilder` already on the compile classpath. Add negative-lookup memoization to `FileFinder` so a repeated miss stops re-running six classpath probes, ~34 stat calls, a depth-5 tree walk and an O(n×m) Levenshtein pass against every discovered file. Hoist the loop-invariant CWD resolution out of `performDiscovery`'s `forEach` and filter on `getFileName()` rather than materializing the full path string. Hoist the three quadratic scans in the Excel analytics path (descendant counting, the two linear finders in `createArraySection`, and the tree generator) onto prebuilt index maps. Hoist `NexusPiercerPatterns`' recompiled suffix regex, replace the unbounded driver `collectAsList` with a bounded/broadcast join, replace the N-literal `isin` with a broadcast join, make `orderBy` opt-in, and read the input once instead of twice in `generateDataQualityReport`.

**Expected gain.** Cache correctness dominates cache speed here, and the honest framing is that the throughput gain is a side effect. The identity-hash keys mean that in the normal streaming pattern — parse the schema per micro-batch — the hit rate is effectively 0%, so every batch rebuilds an entire converter tree; going content-keyed takes that to ~100% and the observed gain is therefore bimodal: near-zero on a benchmark that reuses one Schema object (which is what a naive JMH harness does) and very large on a harness that re-parses per iteration. The benchmark must be written the second way or it will measure nothing, and I expect this to be the iteration where the harness design matters more than the code change. `FileFinder` negative memoization: large for schema-probing loops, irrelevant otherwise. The Excel and Patterns fixes are offline-path only — they turn a multi-minute report on a 5,000-field schema into seconds and remove an unbounded driver collect, but they do not touch per-record throughput at all and should not be quoted as if they did.

**Risk.** Low. Phase 4 already carries the semantic risk (a bounded cache can now evict, so anything depending on a cache entry surviving indefinitely breaks — but nothing should, and the current unbounded behaviour is a driver heap leak). The `FileFinder` negative memoization needs a short TTL or a hot-schema-deployment scenario will keep reporting a file as missing after it appears.

**Validation.** A cache benchmark that re-parses the schema each iteration (not one that reuses a single object), asserting hit rate and throughput; a heap-retention test confirming that N distinct schemas retain O(maximumSize) entries rather than O(N); a `FileFinder` benchmark over repeated identical misses; an Excel-export timing test on a 5,000-field schema; a physical-plan assertion that `NexusPiercerPatterns` performs zero driver collects.

## Iteration 9 — JIT inlining: split the oversized hot methods (speculative until measured)

**Targets:** `perf-avro/RECON-08`, `perf-flatten/JFLAT-09`

**Change.** Split the five hottest reconstruction methods so the per-element inner bodies fall under the 325-byte `FreqInlineSize` threshold. `convertPrimitive` is the cleanest: extract the FIXED decode strategies (~700 of its 1,628 bytes) into a cold `decodeFixed()` and the BYTES branch into `decodeBytes()`, leaving a small hot switch over INT/LONG/STRING/DOUBLE. Do the same for `reconstructNestedRecordFromArray` (1,932 bytes) by hoisting the asymmetric-array default-value block and the nested-array-JSON block. Reorder switch arms so statistically common types come first. Note `reconstructRecord` at 481 bytes is also over threshold. Also fix the batch-processing path: accept a caller-supplied `ExecutorService` instead of building a pool per call, chunk into `batchSize` sublists instead of submitting one task per item, and replace the boxed-index `ConcurrentHashMap` result collection with a preallocated array — though note this path is opt-in and never executes at the default `parallelism = 1`.

**Expected gain.** Genuinely uncertain, and I am flagging it as the most speculative item in the campaign rather than assigning it a number I cannot defend. The mechanism is real and verified — all five methods are 3–6x over `FreqInlineSize` and will never be inlined into their calling loops, which blocks scalar replacement of the per-element temporaries they return. But the blocked optimization is narrower than the finding implies: intra-method escape analysis still runs, so what is actually lost is scalar replacement of returned temporaries and cross-call check elision, not all EA. Plausible range 1.0–1.4x on the array-of-records path, with a real possibility of no measurable change once iteration 4 has removed the dynamic dispatch that currently inflates these methods — the bytecode sizes were measured on the Groovy-compiled classes, and the Java port may bring some of them under threshold for free. That is the honest answer: re-measure the bytecode sizes after iteration 4 and only do this work for methods still over 325 bytes. This iteration may correctly turn out to be mostly unnecessary.

**Risk.** Low for correctness (pure method extraction, mechanically verifiable), but non-trivial for maintainability — splitting methods purely to satisfy a JIT threshold adds indirection that a future reader will not understand unless it is documented, and a future refactor can silently push a method back over the line. Mitigate by adding the hot-method bytecode-size assertion to the Tier-1 gate so the threshold is enforced by CI rather than by memory. If the measured gain is inside the noise band, revert the split and keep only the gate.

**Validation.** Bytecode size of every annotated hot-path method under 325 bytes (Tier-1 deterministic gate); `-prof comp` showing changed compilation behaviour; JMH delta on array-heavy and mixed-production — and an explicit written decision to revert if the delta does not clear the gate band, recorded in `PERFORMANCE.md` as a negative result rather than quietly merged.
